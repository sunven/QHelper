# QHelper 产品方向探索

日期：2026-10-08。状态：待用户研究验证的建议，不是已批准的开发路线图。

## 判断与前提

暂按目标为「服务前端/全栈开发者，积累持续使用」分析。若目标是个人练习，工具广度本身可以有价值；若目标是收入，还需要额外验证采购者、付费动机与获客方式。

建议暂停以工具数量衡量进展，优先验证定位：**帮助开发者把浏览器中的接口问题，整理成可对比、可解释、可交接的证据。**

AI 降低了单次生成、解释和转换的门槛，但确定性工具仍有即时、准确、本地处理的价值。问题是这些功能通常不足以让用户专门安装并持续使用一个新扩展。浏览器现场也不是永久壁垒；必须证明 QHelper 在具体任务中比 DevTools、已有扩展和 AI 工作流更省事。

本文依据仓库能力做机会分析，没有用户访谈、留存数据或当前竞品实测支撑，优先级是研究假设。

## 现有资产与取舍

- `lib/registry/tools.ts`：已有 28 个普通工具，覆盖转换、格式化、安全、图片和数据处理。单点功能广度已经足够支撑实验。
- `lib/context-hub/` 与 `docs/specs/qhelper-context-hub.md`：已有本地识别，JSON、URL、Base64 可携带原文进入临时会话。下一步要验证完整任务收益，单纯增加识别种类未必提高价值。
- `entrypoints/devtools/index.ts` 与 `lib/fe-tools/json-string.ts`：已有可选启用的 JSON 请求捕获和嵌套 JSON 字符串处理。目前限定 localhost、127.0.0.1 和代码匹配的 192.168 主机，不是任意页面的通用诊断系统。
- JSON、文本 Diff、JSON Schema、文本预览、快照等能力可以成为接口排查流程的构件，但组合流程尚未实现。
- Side Panel 网页总结已有入口与 API 配置。通用总结与核心开发调试场景联系较弱，暂不作为增长主线。
- `docs/ROADMAP_REQUIREMENTS.md` 的旧目标是快速增加大量工具，建议在验证后改为任务完成与重复使用目标。

保留并维护 JSON、编码、时间戳、URL、Diff 等基础能力；降低进制转换、UUID、图片拼接、独立代码压缩等功能的新增投入。是否隐藏或删除，应观察真实使用再决定。书签、GitHub 按钮、下载清理可以继续作为便利功能，但暂不扩展为新的产品主线。

## 三个视角，各五个想法

### 产品经理：围绕任务和用户价值

1. **接口差异排查**：比较成功/失败或修改前后的两份 JSON 响应，定位字段变化。
2. **问题交接包**：把用户选定的请求、差异、复现步骤整理成可复制的 Markdown。
3. **登录问题检查**：围绕一次登录失败整理重定向、Cookie 属性、Token 时间信息；复杂度和权限成本较高。
4. **接口契约核对**：把真实响应与用户提供的 Schema 对照，输出具体违规字段。
5. **团队排查模板**：复用团队常见问题的检查步骤与导出格式，作为后续付费假设。

### 产品设计师：减少操作与理解成本

1. **选中即处理**：网页选中文本后直接进入带原文的处理流程。
2. **问题会话**：将输入、转换结果与对比组织成一次问题处理过程，避免反复复制。
3. **字段就地解释**：在 JSON 字段旁展开时间戳或编码内容，同时保留原值。
4. **导出预览与脱敏**：导出前直观看到将分享的内容并编辑敏感字段。
5. **任务入口**：用“比较两份响应”“解析这段数据”验证是否比工具名称目录更容易上手。

### 软件工程师：利用已有能力

1. **请求到分析的直接传递**：把用户选中的已捕获 JSON 响应送到已有处理工具。
2. **结构化 JSON Diff**：按字段路径比较类型、值与缺失项；数组语义需要明确，不能只包装文本 Diff。
3. **确定性字段检查**：识别嵌套 JSON、常见时间戳及用户指定的编码，逐步展开且保留来源。
4. **有证据的 AI 解释**：仅对用户选择的差异生成解释，区分观察事实、原因假设与验证步骤。
5. **可导出的本地样本**：把处理后的样本导出供测试使用，不扩展成完整 API 客户端或自动请求重放。

## 综合优先级：五个候选

排序综合场景契合、预期影响、工作量、差异化；未使用缺少数据支撑的精确分数。以下应串行验证，不是五条同时开发的主线。

| 排名 | 想法与一句话说明 | 为什么选它 | 工作量/差异化判断 | 关键待验证假设 |
| --- | --- | --- | --- | --- |
| 1 | 接口差异排查：把两份 JSON 转为可定位的字段差异 | 任务具体，能复用 JSON、Diff 和请求入口；最容易衡量是否省时 | 手动输入版中等；结构化比较与 DevTools 集成为中到高。优势需要来自整个流程 | 用户经常比较两份响应；结果比现有方法更快；能看懂数组与类型差异 |
| 2 | 问题交接包：把选定证据导出为便于他人接手的问题描述 | 将个人处理结果变成协作产物，可与第一项连成闭环 | 手动编辑导出中等；可靠自动脱敏复杂。仅生成 Markdown 差异化不足 | 真实排查存在反复补充信息；接收方觉得内容有用；准备成本低于手写 |
| 3 | Context Hub 任务流程：识别后直接完成解析、展开或比较 | 复用最多，适合作为前两项入口，能减少跨工具复制 | 低到中；单独作为通用入口容易被替代 | 当前瓶颈确实是选择工具和搬运数据；统一入口提高重复使用 |
| 4 | 接口契约核对：真实响应对照用户提供的 Schema | 有明确对错，已有验证器，适合 AI 生成代码后的人工验收 | 手动粘贴版低到中；直接接入请求为中。不能替代 CI 契约测试 | 目标用户手头有 Schema；浏览器现场检查比回到 IDE 更方便 |
| 5 | 有证据的 AI 解释：基于选定差异提出可验证的原因假设 | AI 用在归纳和排查建议上，建立在可检查的事实之上 | 中到高，需单独设计数据选择、发送和质量评估；竞争强 | 用户需要解释而非只看差异；愿意配置接口；解释能改变下一步行动 |

建议第一个实验只做第 1 项的最小闭环。第 2、3 项根据观察到的瓶颈加入；第 4、5 项暂缓。登录诊断、团队模板暂未入选五强，因为范围、权限或团队采用成本更高。字段展开是小增强，优先用于支持主任务。

## 建议的第一轮验证

以可投入约四周的个人开发节奏为例，时间是预算而非承诺。

1. 第一周：找 5–8 位近期做过接口联调的前端/全栈开发者，让他们重演最近一次失败排查。记录实际工具、复制次数、耗时、如何交接；不要先演示方案再询问是否喜欢。
2. 第二周：用现有功能拼出手动粘贴两份 JSON、比较、复制关键差异的最小体验。观察同一批用户用真实或自行脱敏的样本完成任务。原型阶段不需要新增网络捕获权限，也不需要调用模型。
3. 第三周：只修复阻断任务的最大问题。如果搬运数据是主要瓶颈，再接入现有受限请求入口；如果问题是差异不可读，先改善结果呈现。
4. 第四周：检查是否在不同日期有自然复用，再决定投入请求集成、交接包或 AI 解释。

预先约定的探索门槛示例：5 位试用者中至少 3 位在一周内于两个不同日期主动复用；真实任务的中位完成时间比原工作流减少约 30%；至少 2 位愿意继续用于下一次排查。小样本用于决定下一轮实验，不代表产品市场匹配。

核心指标是“完成真实排查任务并再次使用的人数”，同时观察任务频率、结果正确性、关键字段是否遗漏。通过观察、访谈和用户主动提供的记录采集，不自动增加遥测。

若任务本来每月才发生一次，不要靠增加功能追求周留存；重新选择更高频场景，或接受低频工具的定位。若现有工作流同样快，停止扩大该方向。

## AI 与商业化边界

格式化、解码、Diff、Schema 校验继续由确定性代码完成。AI 可解释和建议，但推断必须与实际观察分开。新增开发数据 AI 功能需要用户明确选择并触发发送；现有网页总结配置不等于已授权上传请求或日志。

若目标是收费，重点验证团队是否愿意为共享排查模板、标准化交接和持续协作付费。单纯提供转换器或要求自带 API Key，没有形成可靠的付费理由。先获得具体试用和付费承诺，再投入账号、云同步、团队权限和订阅系统。

若目标是作品集，则可把“一个完整的浏览器排查闭环”作为展示成果，强调真实问题、设计取舍和验证过程；不必追求工具数量。
